# CLAUDE.md — ClearSlate

Project memory and decisions. Read this first.

## What this is
**ClearSlate** — a fintech app built around a **debit card that enforces the user's own spending rules** to get them out of debt. Set rules during onboarding (block gambling, cap fast food, round up purchases toward debt); the card enforces them at authorization time. Mission: **get people out of debt.**

## Key decisions & context
- **Enforcement model:** hardcore / cold-turkey auto-decline of banned categories (not soft pre-approval friction). Critical constraint: declines must never embarrass the user in front of others, or they churn.
- **Stack (decided):** **Node + TypeScript (Fastify)** + Postgres + Redis; **Drizzle ORM** for schema/migrations, **zod** for env validation. Local infra via **Docker Compose**. Deploy on Railway/Render. Chosen over Python for first-class Plaid/Unit/Marqeta SDKs and single-language sharing with a future RN/web frontend. Charts via Chart.js/Recharts; push via Expo/Firebase; analytics via Mixpanel/PostHog. Backend lives in [backend/](backend/).
- **Frontend (decided):** **React Native via Expo** in [mobile/](mobile/) — TypeScript. Uses `react-native-plaid-link-sdk` (native module → requires a dev build, **not Expo Go**). Backend URL auto-derived from the Metro host. No auth yet (placeholder `demo-user`).
- **Integrations:** Plaid (linking + transactions via cursor-based `transactionsSync`, **done — verified live in sandbox**), Unit (BaaS/KYC/ACH — **token live: auth verified 2026-06-22, `GET /accounts` → 200**; ACH sweep still needs `UNIT_COUNTERPARTY_ID` set), Marqeta (card issuing + JIT — **sandbox creds live, auth verified**; issuance + JIT code built, see Phase 2 note).
- **Onboarding insights (decided):** interest/payoff math uses a **fixed default APR of 24.99%** (`DEFAULT_APR`, shown as an estimate). **Payoff chart baseline (revised 2026-06-19):** the "Now" line is the user's *real* monthly debt payment (Plaid `loan_payment` outflows, ~90-day avg via `monthlyDebtPaymentCents`), falling back to a realistic card minimum (interest + 1% principal, $35 floor) only when none is detected (`baselinePaymentCents`). The "ClearSlate" line = that payment **plus** the cash freed by capping/blocking impulse categories (`IMPULSE_BUCKETS`, floored at `EXTRA_MONTHLY_FLOOR_CENTS`=$50). Replaces the old slider-goal-driven projection, which made small debts look like a 13-month slog and showed ~$0 saved. Pure helpers `baselinePaymentCents` + `payoffComparison` in `apr.ts` (unit-tested, `test/payoff.test.ts`). Insight logic is **server-side** in `backend/src/insights/` (categorize, apr, framing, aggregate, config) and exposed via `GET /onboarding/insights`. Non-spend flows (transfers/loan payments/income) are excluded from budget/overspend math. Charts use **react-native-gifted-charts** (Recharts/Chart.js are web-only).
- **DB tables:** `plaid_items` (encrypted token + sync cursor), `onboarding_responses` (money as integer cents), `transactions` (raw Plaid txns + internal bucket), `enforcement_rules`. - **Phase 3 (Gamification & progress) step engine: COMPLETE.** Step *definitions* are logic-bearing config in code (`backend/src/steps/catalog.ts` — 5 steps, criteria `auto_cashflow`/`auto_debt`/`manual`); only per-user completion persists (`user_steps`, composite PK = idempotent). **Financial-state ladder (revised 2026-06-22):** the ladder is **no longer a strict prefix** — position is derived **live** from real finances so a user's spot reflects their actual state, not how many manual milestones they've ticked. Two **hard gates** decide where they "are": **Step 1 "Stop the bleeding"** = `auto_cashflow` (did last calendar month end **net non-negative**, income ≥ real outflows; falls back to the old discretionary-spend-≤-budget check **only when no income is detectable**, since Plaid sometimes books paychecks as transfers — `bleedingStopped()` in catalog), and **Step 3 "Debt snowball"** = `auto_debt` (debt cleared). The two **savings** steps (starter fund, full safety net) are now **`optional` milestones that never block** — status `"available"`, self-attestable wherever the gates *below* them pass (`manualReachable`); a debt-free, cash-flow-positive user therefore lands on **Invest** with the savings steps left open, and a relapse into net-negative spending pulls "current" **back** to Stop the bleeding (auto-gate display status is recomputed every eval, never pinned by a past completion). `engine.ts`: `buildLadder` (frontier = lowest unsatisfied gate; statuses done/current/available/locked), `evaluateUser` records one-time gate crossings for celebration/dedup only (debt payoff celebrated **only if `startingDebtCents>0`**), `attestStep` gated by the unmet gate below (409), not by other optional steps. `metrics.ts` now also derives `lastMonthIncomeCents`/`lastMonthOutflowCents`/`hasIncomeData` (income = negative Plaid amounts in the `income` bucket; outflows = all positive amounts except internal `transfer`; the old `activeRuleCount` rule-requirement was **dropped** from the Step-1 gate). `notify.ts` + `push/expo.ts` send deduped level-up + 50%/80% progress pushes. Fires off the response path on **rule save** and **Plaid sync**. Advice (`advice.ts`) per step. Mobile: `StepLadder` (Progress tab) renders done/current/**available(OPTIONAL)**/locked + progress bar + tip + per-step inline attest (any reachable manual step, not just "current"), with an in-app level-up `CelebrationModal`. 28 step specs (`test/steps.test.ts`), **215 vitest total green**. Remaining: evening-timing push scheduling, real device tokens (shared decline-push gate), beta recruiting/analysis.

- **Performance rule:** card authorization (Marqeta JIT webhook) must respond < 150ms; rule/MCC/velocity checks read from Redis, never Postgres, in the hot path. **Met** (p99=35ms at a sustained 2000 auth/s; single-process low-latency capacity ≈2000 rps, scales horizontally).
- **Money handling:** round-ups accumulate per user with an audit log (`roundup_ledger` + `roundup_balances`). ✅ **Decided & built end-of-month:** nightly ACH is uneconomical (~$1 fee to move ~$0.01), so the sweep batches one Unit ACH per user per month (`roundup_transfers`, idempotent). Accrual happens at **settlement** (settled amount), not auth.
- **Card vault (behavioral): COMPLETE (code + tests).** Other cards frozen behind deliberate friction (digital "block of ice"). **PAN-free by design** (security call): we store only nickname + last four (non-sensitive, also the unlock key) + network/color — **no card photo, no full PAN** (keeps us out of PCI scope). `vaulted_cards` (migration 0015). **Behavioral redesign 2026-06-21 (time-friction over effort-friction):** unlocking is now a **two-phase, mandatory time-delayed** act, not an instant retype — effort-friction only stops mindless use, whereas a **cooling-off delay** lets a hot-state impulse fade before the card can be spent (Loewenstein's hot/cold empathy gap). Pure state machine in `backend/src/vault/config.ts` — `vaultState()` (replaces `lockState`) derives **sealed → pending → open** from timestamps with lazy reseal: `COOLDOWN_MS`=1h (request → usable) then `UNLOCK_WINDOW_MS`=10min usable window. Three behavioral levers added (per user pick; skipped personalized-cost framing + escalating friction): (1) **pre-committed pledge** `allowed_use` captured at the calm seal moment, confronted at the hot unlock moment ("you sealed this for X — is this that?", an implementation intention); (2) **sealed-day streak** (`sealedDays`, pure-derived; reset only when a card actually *opens*, **preserved if you cancel during the cooldown** — rewards backing off) shown as loss framing at unlock; (3) **reason history** (`vault_unlock_events` table, `recentReasons` reflected back to surface the user's own pattern). `routes/vault.ts` (all IDOR-filtered by userId): `POST /vault/:id/unlock` now = **request** (validates last-four, starts cooldown, logs the reach, bumps `unlockCount`, texts the partner **at the reach so they can intervene during the wait**); `POST /vault/:id/lock` = cancel-pending / reseal-open; `GET /vault/:id/history`. Migration **0018** (allowed_use, unlock_requested_at, unlock_available_at, sealed_since cols + vault_unlock_events table). No hot-path/Redis involvement (off-platform cards). Mobile: 3-phase `VaultCard` (sealed/cooling-off/open w/ per-phase art + countdowns, confront modal w/ pledge + streak-loss + reason history, `ScrollToLock` reseal), pledge field in the seal form, updated `VaultIntroModal` (cooling-off explainer, `INTRO_SEEN_KEY` bumped v2), full bank-vault-themed `VaultScreen` (interior backdrop + door-slam) on the **Rules tab** footer. Tests: pure `vaultState` (phase + streak) + route flow incl. IDOR & cooldown (14 vault specs, `test/vault.test.ts`; **197 vitest total green**). Deferred: real device-local card photos (`expo-image-picker`, never uploaded).
- **Strict Mode (commitment device): COMPLETE (code + tests).** Replaced the old per-category block-lock (2026-06-21): instead of pinning one `block`, a user locks their **whole rule set** for **up to 31 days** so their future self can't go soft (a Ulysses contract). Engaging it **snapshots the current enabled rules as a floor**; while active, every save can only get **stricter** — `resolveStrictRules` re-adds a dropped rule, coerces a downgrade back, clamps a raised cap to the floor (min wins), and keeps round-up / Save-X on; **tightening** (Allow→Cap→Block, lower cap) always passes. Pure logic in `backend/src/strict/config.ts` (`MAX_STRICT_DAYS`=31, `clampStrictDays`, `strictUntilFromDays` — server-authoritative expiry, never trusts the client clock; `strictState` → `{active,strictUntil,daysLeft}`; `floorFromRules`; `resolveStrictRules`). Persisted in the new per-user `strict_modes` table (userId PK + `strictUntil` + jsonb `floor`; migration **0019**, which also **drops the now-dead `enforcement_rules.locked_until`** from the old block-lock). Enforced **only on the rule-SAVE path** (`POST /onboarding/rules` loads the strict row in-tx, resolves, then replaces) — the **auth hot path is unchanged** (no Redis/JIT involvement, no perf impact). Endpoints: `POST /strict-mode` `{days:1..31}` (extend-only — snapshots the floor on fresh engage, keeps it on extend; **no cancel/shorten**) and `GET /strict-mode`. Mobile: self-fetching `StrictModeCard` in the **Rules-tab footer only** (never onboarding) — duration chips (1wk/2wk/1mo) + irreversible-action `Alert` + active countdown banner; `RulesEditor` lost all per-category lock UI and now **re-syncs from the server after an edit-in-place save** so any coercion snaps back visibly. Tests in `backend/test/strict.test.ts` (pure math + route invariants incl. coerce/tighten/extend; **200 vitest total green**).
- **Partner removal cooldown (commitment device): COMPLETE (code + tests).** Removing your accountability partner runs on a **24h cooldown** (`REMOVAL_DELAY_MS`) so you can't ditch oversight the instant you want to slip. `DELETE /accountability/partner` no longer deletes immediately — it sets `accountability_partners.removal_requested_at` (migration 0017), keeps the partner **active** (still gets slip/milestone texts) during the window, and **texts the partner** that removal was requested. `POST /accountability/partner/keep` cancels it; re-adding the same partner also cancels. Pure logic in `backend/src/accountability/removal.ts` (`removalState()` → `{pending, removesAt, elapsed}`, server-authoritative expiry). Finalization is **lazy**: `GET /accountability/partner` deletes the row once elapsed (no cron); `notifyPartner` skips an elapsed-but-unfinalized partner. Mobile `PartnerCard`: `Alert` confirm → pending-countdown banner + "Keep my partner" cancel. Tests in `test/accountability.test.ts` (pure math + cooldown/cancel/finalize route flow; 114 vitest total green).
- **Behavioral Analytics suite ("Your Spending Brain"): COMPLETE (code + tests).** Insight layer beyond a normal bank — models *why* the user spends, not just categories, off `transactions` + precise `auth_events` timestamps. Five pure-core+thin-db modules in `backend/src/insights/behavioral/` (mirror `apr.ts`): `temporal.ts` (day×time heatmap, late-night index, payday cliff), `cascades.ts` (gateway/binge sessions, what-the-hell cascade), `archetype.ts` (deterministic 6-archetype classifier + counter-identity), `futureself.ts` (impulse leak compounded at 7% over 10/20/30y), `leaks.ts` (small+frequent charges annualized). Each exposed via `GET /insights/behavioral/{fingerprint,cascades,archetype,future-self,leaks}` (own route plugin in `routes/behavioral/`, `app.authenticate`-guarded, userId from token — IDOR-safe) and a self-fetching mobile card in `mobile/src/components/behavioral/`, composed into the Insights tab (`SpendingScreen`) as a "Your spending brain" section. Each surfaced number carries a named behavioral hook (ego depletion, licensing/what-the-hell, identity-based change, hyperbolic discounting, latte factor/denominator neglect), framed toward change not shame. Built by 5 parallel agents (create-only file partition since non-git tree); 75 new vitest specs (**189 total green**), backend+mobile tsc clean. **Data note:** intra-day time-of-day comes only from card `auth_events` (Plaid txns are date-only), so the temporal/Midnight-Spender signals stay dormant until real card auths flow — modules degrade gracefully (honest empty states). **Cascade gateway reliability (revised 2026-06-21):** the "your spirals start at X" claim now has a strict bar — `detectGateway` only attributes an opener from *timestamped* sprees (date-only rows share a midnight `at`, so their intra-day order is unknowable; same dormancy as the fingerprint), and only when it repeats >= `MIN_GATEWAY_OPENS`=3 AND holds >= `MIN_GATEWAY_SHARE`=0.4 of timestamped sprees; a specific merchant is named only if it itself repeats (>=2 & majority within the bucket), else we fall back to the category. Below the bar `gateway` is null and the mobile card shows the order-independent cascade magnitude ("what-the-hell effect") instead of fabricating a trigger. So today (no live card auths) the named trigger correctly stays dormant. 205 vitest total green.
